# ZoeAdmin - ប្រព័ន្ធគ្រប់គ្រងអីវ៉ាន់ (Admin)

**ZoeAdmin** គឺជាកម្មវិធីគេហទំព័រ (Web App) សម្រាប់បុគ្គលិកគ្រប់គ្រង (Admin) ប្រើសម្រាប់បញ្ចូល និងគ្រប់គ្រងទិន្នន័យកញ្ចប់ទំនិញ (Parcel/Package) របស់អតិថិជនទាំងអស់ ចាប់ពីការស្កេន Barcode បញ្ចូលកញ្ចប់ថ្មី រហូតដល់ការគណនាប្រាក់ត្រូវទារ (COD/DOD) និងស្ថិតិចំណូល។ កម្មវិធីនេះជា **App គ្រប់គ្រងសំខាន់ (Main Admin)** នៃប្រព័ន្ធ ដែល **ZoeW** (កម្មវិធីទទួល/តាមដានកញ្ចប់) និង **Zoescan** (កម្មវិធីកំណត់ទីតាំង Locker) ទាំងពីរ អានទិន្នន័យរួមគ្នាតាមរយៈ Firebase Database ដូចគ្នា ប៉ុន្តែម្នាក់ៗមានសិទ្ធិខុសគ្នាទៅតាមតួនាទី (Role)។

កម្មវិធីនេះជា **PWA (Progressive Web App)** អាចដំឡើងលើទូរស័ព្ទ ឬកុំព្យូទ័របាន ហើយប្រើ **Firebase** (Authentication + Realtime Database) ជា Backend សម្រាប់ការចូលប្រើប្រាស់ និងផ្ទុកទិន្នន័យ។ Service Worker ទាញយកកូដថ្មីនៅផ្ទៃខាងក្រោយដោយស្វ័យប្រវត្តិនៅពេល Deploy ថ្មី ហើយអនុវត្តនៅពេលបើកកម្មវិធីលើកក្រោយ (មិនរំខានវគ្គដែលកំពុងប្រើប្រាស់ទេ, មិនចាំបាច់ដំឡើង PWA ថ្មីទេ)។

## លក្ខណៈពិសេស (Features)

- 🔐 **ការចូលប្រើប្រាស់សុវត្ថិភាព** — ចូលប្រើប្រាស់តាមរយៈ Firebase Authentication (Email/Password), ត្រូវមានតួនាទី `admin` ជាមុនសិន (គណនី `worker`/`scanner` នឹងត្រូវបដិសេធ ចេញពីប្រព័ន្ធភ្លាមៗ), និងកូដ PIN សុវត្ថិភាពសម្រាប់ការកំណត់រចនាសម្ព័ន្ធ
- 📷 **ស្កេន Barcode** — ស្កេនតាមកាមេរ៉ា (Camera), ម៉ាស៊ីនស្កេន Bluetooth/USB, ឬវាយបញ្ចូលដោយដៃ
- 📦 **បញ្ចូល/គ្រប់គ្រងកញ្ចប់** — កត់ត្រាកញ្ចប់ថ្មីតាមលេខទូរស័ព្ទអតិថិជន, កូដ Barcode ច្រើនក្នុងកញ្ចប់តែមួយ, និងកែប្រែព័ត៌មានអតិថិជន
- 💰 **គណនាប្រាក់ COD/DOD** — គណនាទឹកប្រាក់ត្រូវទារជា USD ($) និង Riel (៛) ដោយស្វ័យប្រវត្តិ តាមអត្រាប្តូរប្រាក់ដែលកំណត់បាន
- ⚙️ **កែប្រែស្ថិតិដោយដៃ** — កែប្រែ COD, DOD និងចំនួនកញ្ចប់ដោយដៃ សម្រាប់ថ្ងៃជាក់លាក់ណាមួយ (ប្រព័ន្ធព្រមានប្រសិនបើខែដែលកែប្រែហួសពីរយៈពេលរក្សាទុក ៣ខែចុងក្រោយ ព្រោះការកែនោះនឹងបាត់វិញ)
- 🏷️ **កែប្រែតម្លៃ Barcode** — កែប្រែ ឬលុប Barcode នីមួយៗក្នុងកញ្ចប់
- 📊 **ស្ថិតិចំណូល** — របាយការណ៍ចំណូលប្រចាំថ្ងៃ និងប្រចាំខែ (COD & DOD ៣ ខែចុងក្រោយ)
- 👥 **ស្ថិតិអតិថិជនយក (Persistent)** — រាប់ចំនួនអតិថិជនតែមួយម្នាក់ៗ (តាមលេខទូរស័ព្ទ) ដែលបានយកកញ្ចប់រួចប្រចាំថ្ងៃ ព្រមទាំងចំនួនកញ្ចប់ (Barcode) ដែលបានប្រគល់ជូនរួច — កត់ត្រាទុកអចិន្ត្រៃយ៍ក្នុង Firebase ដូចស្ថិតិចំណូលដែរ ដូច្នេះលេខមិនថយចុះវិញទេ ទោះកញ្ចប់ដែលបិទរួចហួស ២ម៉ោង ត្រូវផ្លាស់ទីទៅធុងសំរាមស្វ័យប្រវត្តិក៏ដោយ
- 🔍 **ស្វែងរក & Lookup API** — ស្វែងរកកញ្ចប់តាមលេខទូរស័ព្ទ (រកឃើញគ្រប់ថ្ងៃ ទោះកំពុងជ្រើសរើសតម្រងកាលបរិច្ឆេទផ្សេងក៏ដោយ; វាយត្រឹមកន្ទុយលេខ ៣-៤ ខ្ទង់ក៏ដុំស្នើលេខលោតមកដែរ) ព្រមទាំងភ្ជាប់ API ខាងក្រៅ (ឧ. Google Sheet/Apps Script — មើលផ្នែក "Lookup API" ខាងក្រោម) សម្រាប់ស្វែងរកព័ត៌មានអតិថិជនស្វ័យប្រវត្តិពេលស្កេន Barcode, ជាមួយជម្រើសរក្សាទុកភ្លាមៗស្វ័យប្រវត្តិ (មិនចាំចុច "យល់ព្រម") ពេលរកឃើញលេខទូរស័ព្ទត្រូវគ្នា
- 🗑️ **គ្រប់គ្រង "លុប" (លុបជាកញ្ចប់)** — លុបកញ្ចប់ទាំងមូល (លុប = "លុប") ចូល "ទិន្នន័យលុបបណ្តោះអាសន្ន" ដោយ **មិនប៉ះពាល់ស្ថិតិចំណូលឡើយ** (ស្ថិតិប្រចាំថ្ងៃ/ខែនៅដដែលជានិច្ច ទោះស្តារ ឬលុបម្តងទៀតក៏ដោយ) ព្រមទាំងស្តារទិន្នន័យត្រឡប់មកវិញបាន និងលុបជាអចិន្ត្រៃយ៍ (មានប្រអប់បញ្ជាក់ពីរដង)
- ✂️ **ដកកញ្ចប់ (ដកចេញពី Barcode ច្រើន)** — ដកតែ Barcode តែមួយចេញពីកញ្ចប់ (ដក = "ដក") **ដកតម្លៃ/ចំនួនចេញពីស្ថិតិផងដែរ** ហើយស្តារ/ដកម្តងទៀតនឹងបូក/ដកតម្លៃត្រឡប់ទៅវិញដោយស្វ័យប្រវត្តិ (មិនស្ទួន មិនបាត់)
- ⏰ **ច្បាប់លុប/ដកស្វ័យប្រវត្តិ** — កញ្ចប់ដែលបិទបញ្ជីរួច (Closed) លើសពី **២ម៉ោង** ត្រូវលុបស្វ័យប្រវត្តិ (មិនប៉ះស្ថិតិ), កញ្ចប់ដែលនៅសល់មិនទាន់បិទលើសពី **៨ថ្ងៃ** ត្រូវដកចេញស្វ័យប្រវត្តិ (ដកស្ថិតិ), ហើយទិន្នន័យក្នុងធុងសំរាមលើសពី **១០ថ្ងៃ** ត្រូវលុបចោលជាអចិន្ត្រៃយ៍ស្វ័យប្រវត្តិ
- 📤 **Export ទិន្នន័យ** — Export របាយការណ៍ដែលកំពុងបង្ហាញជា Excel (.xlsx), PDF (មានអក្សរខ្មែរច្បាស់ តាមរយៈ browser print-to-PDF, បូកសរុប COD/DOD/ចំនួន, និងលេខទំព័រ/ពេលវេលា Export), ឬ CSV សម្រាប់ Google Sheet។ លេខទូរស័ព្ទ និង Barcode ត្រូវបាន Export ជា **អក្សរ (text)** ជានិច្ច ដូច្នេះលេខ 0 ខាងមុខមិនបាត់ ហើយ Barcode វែងមិនប្រែជាទម្រង់វិទ្យាសាស្ត្រ (7.71305E+13) ទេ
- 📋 **តារាងទិន្នន័យអតិថិជន (Customer Data Table)** — ទិដ្ឋភាព Read-only នៃទិន្នន័យអតិថិជនពី Google Sheet ដែលភ្ជាប់ (មើលផ្នែក "Lookup API" ខាងក្រោម)
- 🔄 **Sync ទិន្នន័យសម្រាប់ Zoescan** — ប៊ូតុង "កំណត់ទិន្នន័យ Scanner Lookup ឡើងវិញ" (ក្នុងម៉ឺនុយ "⋯") សម្រាប់ Sync ទិន្នន័យចាស់ចូល `zoew_scanner_lookup` ប្រសិនបើ Zoescan មិនឃើញកញ្ចប់ណាមួយ
- 🔗 **Setup Link / QR** — ទទួល Firebase Config ពី ZoeKeyGen តាម Link `?setup=` ឬស្កេន QR ក្នុង ⚙️ Config ("📷 ស្កេន QR (Setup Link)") ។ ទាំងពីរផ្លូវឆ្លងកាត់ Security PIN ហើយត្រូវឲ្យមនុស្សពិនិត្យ Config ក្នុង Textarea រួចចុច "រក្សាទុក" ដោយខ្លួនឯង — គ្មានផ្លូវរក្សាទុកស្វ័យប្រវត្តិដោយស្ងាត់ៗទេ
- 📱 **ដំឡើងជា App បាន (PWA)** — គាំទ្រ Service Worker សម្រាប់ប្រើប្រាស់ក្រៅបណ្តាញ (Offline) និងទទួលបានកូដថ្មីស្វ័យប្រវត្តិគ្រប់ពេល Deploy ដោយមិនចាំបាច់ដំឡើងសាថ្មីទេ

## Lookup API (ស្វែងរកអតិថិជនស្វ័យប្រវត្តិ)

ZoeAdmin អាចភ្ជាប់ទៅ API ខាងក្រៅ (ជាទូទៅ Google Apps Script ដែលអាន Google Sheet) ដើម្បីបំពេញ
លេខទូរស័ព្ទ/COD/DOD ស្វ័យប្រវត្តិពេលស្កេន Barcode។ កំណត់ត្រង់ ⋯ ➜ **🔌 API ស្វែងរកអតិថិជន**
(ត្រូវការ Security PIN)។ Endpoint ត្រូវផ្គូផ្គងកិច្ចសន្យាខាងក្រោម៖

| ការកំណត់ | អត្ថន័យ |
|---|---|
| **URL** | ត្រូវមាន `{barcode}` ជាកន្លែងដាក់លេខបាកូដ (ឧ. `https://script.google.com/.../exec?code={barcode}`) |
| **Header Name / Value** | ស្រេចចិត្ត — Secret បញ្ជូនជា HTTP header។ តម្លៃត្រូវបាន **Encrypt ដោយកូនសោដែលមកពី Security PIN** មុនរក្សាទុកក្នុង `localStorage` (មិនរក្សាទុកជាអក្សរធម្មតាទេ) |
| **Phone / COD / DOD Field** | ផ្លូវទៅវាលក្នុង JSON ឆ្លើយតប (គាំទ្រ nested ដូច `data.phone`) — លំនាំដើម `phone`, `cod`, `dod` |
| **Auto Submit** | បើកបាន — រក្សាទុកភ្លាមៗពេលរកឃើញលេខទូរស័ព្ទត្រូវគ្នា (មិនចាំចុច "យល់ព្រម") |

- **ស្វែងរកមួយបាកូដ**៖ `GET <URL ដែលជំនួស {barcode} រួច>` → JSON មានវាល phone/cod/dod
  (បើមានវាល `error` ប្រព័ន្ធចាត់ទុកជាបរាជ័យ)។
- **តារាងទិន្នន័យអតិថិជន**៖ ZoeAdmin ហៅ URL ដដែល ដោយប្តូរ `code=...` ទៅ `list=1`
  (ឬបន្ថែម `?list=1`) → JSON ត្រូវឆ្លើយ `{ "rows": [ { "barcode": "...", "phone": "...",
  "cod": 0, "dod": 0 }, ... ] }` ។ លទ្ធផលត្រូវ Cache ១៥នាទី ហើយប្រើជា Cache សម្រាប់ការស្កេន
  បន្ទាប់ផងដែរ (កាត់បន្ថយការហៅ API)។
- បើ Endpoint យឺត/ដួល ប្រព័ន្ធមាន Timeout + Retry + Cooldown រួចហើយ ហើយការស្កេននៅតែដំណើរការ
  ធម្មតា (គ្រាន់តែមិនបំពេញស្វ័យប្រវត្តិ)។
- Host របស់ Endpoint ត្រូវស្ថិតក្នុង `connect-src` នៃ CSP ក្នុង `netlify.toml` —
  បច្ចុប្បន្នអនុញ្ញាត `script.google.com` និង `*.googleusercontent.com`។ បើប្តូរទៅ Host ផ្សេង
  ត្រូវបន្ថែមក្នុង CSP ជាមុនសិន បើមិនដូច្នេះទេ Browser នឹងបិទការហៅនោះ។

## គោលការណ៍ "លុប" vs "ដក" (Delete vs Remove Policy)

| | លុប (Delete) | ដក (Remove) |
|---|---|---|
| អ្វីខ្លះ | លុបកញ្ចប់ទាំងមូល | ដក Barcode តែមួយចេញពីកញ្ចប់ច្រើន Barcode |
| ប៉ះស្ថិតិចំណូល? | **ទេ** — ស្ថិតិប្រចាំថ្ងៃ/ខែនៅដដែលជាអចិន្ត្រៃយ៍ | **បាទ/ចាស** — ដកតម្លៃ/ចំនួនចេញពីស្ថិតិភ្លាមៗ |
| ស្តារមកវិញ (Restore)? | មិនបូកអ្វីបន្ថែម (ព្រោះមិនធ្លាប់ដកចេញ) | បូកតម្លៃត្រឡប់ចូលស្ថិតិវិញ |
| លុប/ដកម្តងទៀត? | មិនដកអ្វីបន្ថែម (Idempotent) | ដកតម្លៃម្តងទៀត |
| ស្ថានភាព (បានហៅ/បិទបញ្ជី) | រក្សាទុកគ្រប់ពេល ទោះកន្លងកាត់ Delete→Restore→Delete ច្រើនដងក៏ដោយ | រក្សាទុកគ្រប់ពេលដូចគ្នា |
| Marker ក្នុងធុងសំរាម | `isFromDeletion: true` | `isFromDeletion: false` + `isDeducted: true` |

**"បិទ" = "យកហើយ"** — អតិថិជនបានមកយកកញ្ចប់រួច។ ចំនួន និងតម្លៃត្រូវរក្សាទុកក្នុងស្ថិតិជាអចិន្ត្រៃយ៍
ហើយកញ្ចប់នោះលុបចេញស្វ័យប្រវត្តិក្រោយ **២ម៉ោង** ដោយ **មិនប៉ះស្ថិតិ**។ ផ្ទុយមកវិញ កញ្ចប់ដែលមិនទាន់យក
លើសពី **៨ថ្ងៃ** ត្រូវ Return ទៅសាខាកណ្ដាលវិញ ដូច្នេះវាជា "ដក" — ត្រូវដកចេញទាំង **ទឹកប្រាក់ និងចំនួនកញ្ចប់**។

### Marker កត់ត្រាតាម Barcode នីមួយៗ

Barcode នីមួយៗចងចាំដោយខ្លួនឯងថាវាចូលធុងសំរាមតាមផ្លូវណា — មិនមែនត្រឹមកម្រិត Order ទេ៖

| វាល (លើ Barcode នីមួយៗ) | អត្ថន័យ |
|---|---|
| `isFromDeletion: true` | Barcode នេះចូលធុងសំរាមដោយ **លុប** ➜ តម្លៃ/ចំនួន **មិនដែលត្រូវដក** ចេញពីស្ថិតិ |
| `isFromDeletion: false` | Barcode នេះចូលធុងសំរាមដោយ **ដក** ➜ តម្លៃ/ចំនួន **ត្រូវបានដក** រួច |
| `isDeducted: true` | តម្លៃ Barcode នេះកំពុងស្ថិតក្នុងស្ថានភាព "ដកចេញរួច" — ពេលស្តារត្រូវបូកត្រឡប់វិញ |
| `isDeducted: false` | មិនមានអ្វីត្រូវបូកត្រឡប់វិញទេ |

ពេល Barcode ត្រូវស្តារមករស់វិញ Marker ទាំងពីរត្រូវសម្អាតទៅ `false` (វាលែងស្ថិតក្នុងធុងសំរាមទៀត)។
`isDeducted` ជាវាលដែលកំណត់ចលនាទឹកប្រាក់ ចំណែក `isFromDeletion` ជាកំណត់ត្រាថា "ហេតុអ្វីវាចេញ" —
ដូច្នេះទោះ Order មួយត្រូវបញ្ចូល Barcode ពីប្រភពផ្សេងគ្នា (ករណី Restore-merge) Barcode នីមួយៗនៅតែ
ចងចាំប្រវត្តិរបស់ខ្លួនត្រឹមត្រូវ។

នេះជាគោលការណ៍អាជីវកម្ម មិនមែន Bug ទេ។ វាត្រូវបានផ្ទៀងផ្ទាត់ដោយ Test ដែលរត់លើកូដពិតប្រាកដ
(លុប→ស្តារ→លុប→ស្តារ = ស្ថិតិមិនរើទាល់តែសោះ; ដក→ស្តារ→ដក→ស្តារ = ដក/បូកត្រឹមត្រូវរាល់ដង)។

## សុវត្ថិភាព (Security)

- ការចូលប្រើប្រាស់តម្រូវឲ្យមានគណនី Firebase Authentication **ត្រូវជាមួយតួនាទី `admin`** (កំណត់ត្រង់ Server-side តាម `user_roles/$uid` — មិនអាចក្លែងបានទេ)
- **ព្រំដែនសុវត្ថិភាពពិតប្រាកដស្ថិតនៅ Server-side** តាមរយៈ `firebase-database.rules.json` (មិនមែន Client-side ទេ) — Rule កំណត់ច្បាស់ថា `admin`/`worker`/`scanner` នីមួយៗអានសរសេរអ្វីបានខ្លះ
- Scanner (Zoescan) លែងអានឃើញ COD/DOD ឬស្ថានភាពអាជីវកម្មនៃកញ្ចប់ណាមួយបានទៀតហើយ — មានតែ `zoew_scanner_lookup` (លេខទូរស័ព្ទ + Barcode + Locker + `isClosed` តែប៉ុណ្ណោះ) ដែល Scanner អាចអានបាន
- មានកូដ PIN ដាច់ដោយឡែកសម្រាប់ការកែប្រែការកំណត់រចនាសម្ព័ន្ធ (Config)
- ទិន្នន័យទាំងអស់ដែលមកពី Firebase (លេខទូរស័ព្ទ, Barcode, ព័ត៌មានអតិថិជន) ត្រូវបាន Escape មុននឹងបង្ហាញ ដើម្បីការពារការវាយប្រហារ XSS
- Logout លុបទិន្នន័យអតិថិជនចេញពីអេក្រង់ភ្លាមៗ (មិនទុកសល់ឲ្យអ្នកប្រើបន្ទាប់ឃើញ ក្នុងករណីប្រើ Device រួម)
