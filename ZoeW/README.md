# ZoeW — កម្មវិធីគ្រប់គ្រងកញ្ចប់

ZoeW គឺជា PWA តែមួយសម្រាប់គ្រប់គ្រងកញ្ចប់ អតិថិជន ទីតាំង Locker និងស្ថិតិ COD/DOD ក្នុងប្រព័ន្ធ Zoe។

កំណែបច្ចុប្បន្ន៖ **2.12.0** (កំណែតែមួយប្រើរួមគ្នាទាំង ZoeW និង ZoeKeyGen — មើល [CHANGELOG.md](../CHANGELOG.md))។

## តួនាទី និងព្រំដែន

- **គ្មានតួនាទីបំបែក** — គណនី Firebase ណាដែលចូលប្រព័ន្ធបាន មានសិទ្ធិដូចគ្នា។ ការត្រួតពិនិត្យសិទ្ធិពិតស្ថិតនៅ Firebase Realtime Database Rules មិនមែននៅ UI ទេ។
- `zoew_scan_history_cod_dod` ជាទិន្នន័យប្រវត្តិសំខាន់ **តែមួយ** ហើយ App អានវាដោយផ្ទាល់ — គ្មាន projection ជាន់ទីពីរដែលអាចបែកគ្នាទេ។
- រាល់ការកែកញ្ចប់ (បញ្ចូល, ដក, លុប, បិទ/បើក, កែទឹកប្រាក់, កំណត់ទីតាំង) ធ្វើឡើងដោយ `runTransaction` លើ record របស់ server ដោយផ្ទាល់ ដូច្នេះឧបករណ៍ច្រើនមិនសរសេរជាន់គ្នាទេ។

## ការងារប្រចាំថ្ងៃ

1. ចូលប្រព័ន្ធ។
2. ទៅទំព័រ **បញ្ចូលទិន្នន័យ** ➜ របៀប «📦 បញ្ចូលកញ្ចប់» ➜ ស្កេន ឬបញ្ចូល Barcode និងលេខទូរស័ព្ទ។
3. ពិនិត្យ COD/DOD, Barcode និងទីតាំង Locker មុនរក្សាទុក។
4. ដើម្បីដាក់កញ្ចប់ចូលទូ៖ ប្តូរទៅរបៀប «📍 កំណត់ទីតាំង Locker» ➜ ជ្រើសទូបច្ចុប្បន្ន ➜ ស្កេន Barcode ម្តងមួយៗ។
5. បញ្ជី **កញ្ចប់ដែលបានបញ្ចូលថ្ងៃនេះ** នៅក្រោមកន្លែងស្កេន បង្ហាញអ្វីដែលទើបបញ្ចូល (ថ្មីមុនគេ) ហើយស្វែងរកតាមលេខទូរស័ព្ទ ឬ Barcode បាន។
6. នៅទំព័រ **ទិន្នន័យ** ប្រើតម្រងថ្ងៃ, ស្វែងរកលេខទូរស័ព្ទ, ស្ថិតិប្រចាំថ្ងៃ/ខែ និង Export។

## របៀបកំណត់ទីតាំង Locker

- កញ្ចប់ដែល **មិនទាន់មានទីតាំង** ➜ ចុះទីតាំងភ្លាម **គ្មានប្រអប់សួរបញ្ជាក់**។
- កញ្ចប់ដែល **មានទីតាំងរួច** ➜ សួរបញ្ជាក់ជាមុន («តើអ្នកចង់ផ្លាស់ទីកញ្ចប់នេះទៅ … មែនទេ?») ហើយប្រាប់ផងដែរបើទីតាំងគោលដៅមានកញ្ចប់ផ្សេងស្ថិតនៅ។
- កញ្ចប់ដែលស្ថិតនៅទីតាំងដដែលរួច ➜ គ្រាន់តែជូនដំណឹង គ្មានការសរសេរថ្មី។
- Barcode ដែលមិនទាន់មានក្នុងប្រព័ន្ធ ➜ បដិសេធ ព្រមទាំងណែនាំឱ្យបញ្ចូលកញ្ចប់ជាមុនសិន។

បុព្វបទ (Prefix) និងចំនួនទូកំណត់នៅ **របា Slide ➜ កំណត់ទូ Locker** (ក្រោម Security PIN)។

## លុបទាំងអស់

«លុបទាំងអស់» លុប **តែធាតុដែលកំពុងឈរតាមតម្រងថ្ងៃបច្ចុប្បន្ន** ប៉ុណ្ណោះ (ឧ. ឈរលើ «ថ្ងៃនេះ» ➜ លុបតែថ្ងៃនេះ)។ វាទាមទារ **Security PIN** មុនដំណើរការ ដូច «កែទឹកប្រាក់/កញ្ចប់» ដែរ ហើយប្រអប់បញ្ជាក់ប្រាប់ចំនួនធាតុពិតមុនលុប។

## ការស្កេន Barcode

- ទទួល **តែ `CODE_128`** ប៉ុណ្ណោះ (format ដែលកញ្ចប់អីវ៉ាន់ប្រើ)។ format ផ្សេងត្រូវបដិសេធដោយចេតនា ព្រោះពួកវាគ្មានលេខផ្ទៀងផ្ទាត់ជាកាតព្វកិច្ច ➜ អាចអានចេញជាលេខខុស។
- លេខមួយត្រូវអានឃើញ **ដដែល ២ ស៊ុមជាប់គ្នា** ទើបទទួលយក។
- ផ្លូវរូបភាព និង Barcode scanner (Bluetooth/USB) មានតែស៊ុមតែមួយ ដូច្នេះវាមិនឆ្លងកាត់ជាន់ ២ នេះទេ។
- **ការស្កេនកាមេរ៉ាដើរបានទោះគ្មានបណ្តាញ។**
- iPhone យឺតជាង Android ដោយធម្មជាតិ។ គុណភាពឌិកូដលើ iPhone សម្របតាមល្បឿនឧបករណ៍ដោយស្វ័យប្រវត្តិ។

### បើស្កេនមិនចេញ

1. **កាន់ឲ្យ barcode ពេញទទឹងស៊ុមជាង** — ជួរអានកំណត់ដោយទទឹង barcode ក្នុងស៊ុម។
2. ពិនិត្យថាស្លាកជា **CODE_128** មែន (format ផ្សេងត្រូវបដិសេធដោយចេតនា)។
3. បើកភ្លើង (💡) ពេលពន្លឺតិច ហើយប្រើ zoom បើមាន។
4. បើប្រអប់ native (`confirm`/`alert`) បើករួចកាមេរ៉ាកក ➜ បិទបើកកាមេរ៉ាឡើងវិញ។

## Lookup API និង Google Sheets

ZoeW អាចយកលេខទូរស័ព្ទ/COD/DOD ពី endpoint ខាងក្រៅពេលស្កេន Barcode។ កំណត់នៅ **របា Slide ➜ API ស្វែងរកអតិថិជន** ក្រោម Security PIN។

- URL ត្រូវមាន `{barcode}` ឬគាំទ្រផ្លូវដែលកម្មវិធីអាចបញ្ចូល Barcode បាន។
- JSON អាចកំណត់ផ្លូវ `phone`, `cod`, និង `dod` បាន រួមទាំង nested field។
- Header secret ដែលកំណត់ថ្មីត្រូវបាន encrypt ដោយកូនសោពី PIN មុនរក្សាទុកក្នុង browser។
- Google Apps Script ក្នុង [`../zto-import/google-sheets-api/`](../zto-import/google-sheets-api/README.md) គាំទ្រទាំង lookup មួយ Barcode និង `list=1`។ Cache គឺ best-effort ប៉ុណ្ណោះ; នៅពេល payload ធំពេក វាត្រូវ fallback ទៅការអាន Sheet ជំនួសការធ្វើឱ្យ API បរាជ័យ។

បើប្តូរ host របស់ API ត្រូវកែ `connect-src` ក្នុង CSP របស់ deployment ផងដែរ។

## សុវត្ថិភាព និងភាពត្រឹមត្រូវ

- Setup Link/QR មិនរក្សាទុក Config ដោយស្វ័យប្រវត្តិទេ៖ ត្រូវឆ្លង PIN ពិនិត្យ JSON ហើយចុចរក្សាទុកដោយខ្លួនឯង។
- Logout សម្អាតទិន្នន័យកញ្ចប់ បញ្ជីទីតាំង និង form សំខាន់ចេញពី DOM។
- Rules ការពារ **schema** (ប្រភេទវាល, ជួរតម្លៃ, `$other: false`) និង **claim/witness fence** សម្រាប់ Restore/Clear All។ វាមិនបែងចែកតួនាទីទេ។
- កុំទុក PIN, Firebase Config, API secret ឬ export ទិន្នន័យអតិថិជនលើឧបករណ៍សាធារណៈ។

## Deploy និងការបញ្ចេញកំណែ

App នេះជា static site គ្មាន build step។ Deploy ថត `ZoeW` ទៅ hosting របស់វា ហើយប្តូរ `CACHE_VERSION` រាល់ពេល asset ផ្លាស់ប្តូរ។ Service Worker ទាញកំណែថ្មីនៅផ្ទៃខាងក្រោយ ហើយប្រើវាពេលបើក App លើកក្រោយ។

engine ស្កេន (`vendor/zxing-wasm.js` + `vendor/zxing_reader.wasm`) ជាឯកសារ **ក្នុង repo** មិនមែន dependency ដែលត្រូវ build ទេ។ ដើម្បីឡើងកំណែវា៖ `npm i zxing-wasm@<new>` រួច `cp node_modules/zxing-wasm/dist/iife/reader/index.js ZoeW/vendor/zxing-wasm.js` និង `cp node_modules/zxing-wasm/dist/reader/zxing_reader.wasm ZoeW/vendor/` រួចរត់ `scan-engine-test.js` និង `offline-shell-test.js` ឡើងវិញ។ **ត្រូវចម្លងទាំង ២ ឯកសារ** — `offline-shell-test.js` ផ្ទៀងផ្ទាត់ថា binary ត្រូវនឹង sha256 ដែល glue រំពឹងទុក។

**CSP ត្រូវមាន `'wasm-unsafe-eval'`** ក្នុង `script-src` របស់ `netlify.toml` បើអត់ browser បដិសេធការចងក្រង WebAssembly ➜ ការស្កេនស្លាប់លើផលិតកម្ម។

**ចាំបាច់៖** `firebase-database.rules.json` នៅ root មិន deploy តាម Netlify ឬ static hosting ទេ។ មុន release ដែលពាក់ព័ន្ធនឹង Firebase path/rules សូម backup Rules ចាស់, paste ឯកសារនេះទៅ Business Firebase Project ក្នុង Firebase Console, ពិនិត្យ Rules Simulator ហើយចុច **Publish** ដោយដៃ។
