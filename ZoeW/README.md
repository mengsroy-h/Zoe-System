## មុខងារ

### ការស្កេន និងការបញ្ចូល

- **ផ្លូវស្កេន ៣** — កាមេរ៉ា · ម៉ាស៊ីនស្កេន hardware · រូបភាពក្នុងឧបករណ៍។
  គ្រប់ផ្លូវឆ្លងកាត់ចំណុចបំបែកតែមួយ ដូច្នេះឥរិយាបថដូចគ្នាបេះបិទ។
- **Engine ស្កេន ZXing C++ ចងក្រងជា WebAssembly** ស្ថិតក្នុង repo។ លើ Android
  វាប្រើ `BarcodeDetector` ដើមរបស់ប្រព័ន្ធពេលមាន។
- **ទទួលតែ CODE-128** — format ដែលមានលេខផ្ទៀងផ្ទាត់ជាកាតព្វកិច្ច។ ITF, CODABAR
  និង CODE-39 ត្រូវបដិសេធ ព្រោះស្លាកមួយអាចអានចេញជាលេខផ្សេងដោយ «ជោគជ័យ»។
- **ការបញ្ជាក់ ២ ស៊ុមជាប់គ្នា** លើផ្លូវកាមេរ៉ា — ជាន់ការពារទីពីរប្រឆាំងការអានខុស។
- **ជួរអានសម្របតាមឧបករណ៍** — ទទឹងស៊ុមឌិកូដឡើងចុះតាមល្បឿនពិតរបស់ឧបករណ៍។
- **ការទប់ស្កាត់ Barcode ស្ទួន ៥ ជាន់**។
- **របៀបស្កេន ២** — កញ្ចប់ និងទីតាំង Locker។

### ទិន្នន័យ និងចំណូល

- **COD និង DOD** ក្នុងកញ្ចប់តែមួយ ព្រមទាំងលេខទូរស័ព្ទ និងទីតាំង Locker។
- **Barcode ច្រើនក្នុងកញ្ចប់តែមួយ** — កែ ឬដកចេញម្តងមួយបាន។
- **ស្ថិតិប្រចាំថ្ងៃ និងប្រចាំខែ** — ចំណូល ចំនួនកញ្ចប់ និងអតិថិជនយក។
  **អតិថិជនយក** = លេខទូរស័ព្ទផ្សេងៗគ្នាដែលមាន barcode បិទ >= ១;
  **កញ្ចប់យក** = ចំនួន barcode បិទ។
- **Reset ចំនួន «យករួច» តាមតម្រងថ្ងៃ** (កំណែ 2.20.0) — ម៉ឺនុយ (...) ➜
  «♻️ Reset ចំនួនយករួច (<តម្រង>)», **ការពារដោយ PIN**។ វា Reset លេខ
  **អតិថិជនយក** និង **កញ្ចប់យក** ត្រឹម **តម្រងថ្ងៃដែលកំពុងឈរលើ** ប៉ុណ្ណោះ
  (ថ្ងៃផ្សេងមិនប៉ះពាល់)។ ⛔ វា **មិនប៉ះទឹកប្រាក់ COD/DOD ស្ថិតិចំណូល
  បញ្ជីកញ្ចប់ ឬធុងសំរាមសោះ** — barcode ដែលបិទ «យក» នៅតែបិទដដែល; ការរាប់
  គ្រាន់តែចាប់ផ្តើមឡើងវិញពី 0 សម្រាប់ថ្ងៃនោះ។
- **អត្រាប្តូរប្រាក់រៀល** ចែករំលែករវាងឧបករណ៍ទាំងអស់។
- **តម្រងតាមថ្ងៃ** និងការស្វែងរកតាមលេខទូរស័ព្ទ (ចាប់កន្ទុយលេខ ៣–៤ ខ្ទង់
  ព្រមទាំងបញ្ជីលេខថ្មីៗ)។
- **ធុងសំរាម និងការស្តារ** — កញ្ចប់ដែលលុបនៅរស់មួយរយៈមុនលុបចោលពិត។
- **ការសម្អាតស្វ័យប្រវត្តិ** — **Barcode** បិទរួច ➜ ធុងសំរាមក្រោយ ២ ម៉ោង
  ដោយឯករាជ្យពី barcode ដទៃក្នុងកញ្ចប់ដដែល (កំណែ 2.17.2); មិនទាន់បិទ ➜
  ក្រោយ ៨ ថ្ងៃ; ក្នុងធុងសំរាម ➜ លុបចោលក្រោយ ៣០ ថ្ងៃ។ ការសម្រេចទាំងអស់ធ្វើ
  **ខាងក្នុង transaction ធៀបនឹងម៉ោង server** មិនមែនតាមស្ថានភាពក្នុងសតិទេ។

### «លុប» ទល់នឹង «ដក» — គោលការណ៍អាជីវកម្ម

នេះជាការបែងចែកដោយចេតនា មិនមែនកំហុសទេ៖

|---|---|---|
| **លុប** | លុបកញ្ចប់ទាំងមូល (Barcode ទាំងអស់របស់វា) | **មិនប៉ះ** ចំណូលក្នុងទិសណាក៏ដោយ |

## ប្រព័ន្ធសុវត្ថិភាព

### ការចូលប្រើ

| ស្រទាប់ | អ្វី |
|---|---|
| **Activation Key** | ECDSA P-256 sign ដោយ ZoeKeyGen; ផ្ទៀងផ្ទាត់ទាំងក្នុងឧបករណ៍ និងខាង server (`revoked`, ពិដានសុពលភាព); គ្មានបណ្តាញ ➜ អនុគ្រោះ ៣ ថ្ងៃ |
| **Firebase Authentication** | អ៊ីមែល + ពាក្យសម្ងាត់; session ផុតកំណត់ក្រោយ ៤ ម៉ោង |
| **Security PIN** | PBKDF2-SHA256 **១៥០,០០០ ជុំ**; រក្សាទុកតែ hash; វាយខុសច្រើនដង ➜ ចាក់សោ |
| **WebAuthn** | ក្រយៅដៃ/មុខជាការ **ដោះសោ PIN** មិនមែនជំនួសវាទេ; PIN ដែលស្រាយចេញត្រូវផ្ទៀងផ្ទាត់នឹង hash មុនទុកចិត្ត |

**PIN មិនត្រឹមតែជា gate ទេ** — វាជាប្រភពនៃកូនសោ AES ដែលឌិគ្រីប Secret របស់
Lookup API។ ដូច្នេះជីវមាត្រមិនអាចជំនួស PIN ជាប្រភពសម្ងាត់បានឡើយ។

សកម្មភាពដែលការពារដោយ PIN៖ Config Firebase · Lookup API · កំណត់ទូ Locker ·
កែទឹកប្រាក់/កញ្ចប់ដោយដៃ · **Reset ចំនួនយករួច** · លុបទាំងអស់ · Setup Link។

### ទិន្នន័យរសើប

- Secret របស់ Lookup API ត្រូវ **អ៊ិនគ្រីប AES-GCM 256** ដោយកូនសោដែល derive
  ពី PIN មុនចូល `localStorage`។ កូនសោនោះរស់តែក្នុងសតិ ហើយលុបចោលពេលចាកចេញ។
- **ការចាកចេញសម្អាត DOM** — ទិន្នន័យអតិថិជន បញ្ជីទីតាំង និងវាល form សំខាន់
  ត្រូវលុបចេញ ដូច្នេះអ្នកកាន់ឧបករណ៍តទៅអានមិនឃើញ។
- **Setup Link មិនរក្សាទុកដោយស្វ័យប្រវត្តិទេ** — វាត្រូវឆ្លង PIN ហើយ query string
  ត្រូវលុបចេញភ្លាម។ វាក៏មិនអាចជាប់ក្នុង Cache Storage ដែរ ព្រោះសំណើ navigate
  ប្រើ `./index.html` ជាកូនសោ cache ជានិច្ច។
- **របាយការណ៍កំហុសលាក់ secret** — URL parameter រសើប (`auth`, `token`, `key`,
  `setup` ។ល។) ត្រូវជំនួសដោយ `[redacted]` មុនផ្ញើទៅ Sentry។

### ការការពារខាង Browser

- **`script-src` គ្មាន `'unsafe-inline'`** ➜ ទោះមានអក្សរចម្លែកចូលដល់ទំព័រ
  ក៏ browser បដិសេធមិនឲ្យវារត់ដែរ។ ការចុចប៊ូតុងធ្វើតាម `data-act` បូក
  **បញ្ជីអនុញ្ញាត** ដូច្នេះ attribute ក្នុង HTML មិនអាចហៅ function តាមចិត្តបាន។
- **គ្មាន `onclick=` សល់សោះ** ➜ ថ្នាក់កំហុស «escape ២ ជាន់» លែងអាចកើតឡើងបាន
  តាមរចនាសម្ព័ន្ធ។
- **`frame-ancestors 'none'`** · **`object-src 'none'`** · **`base-uri 'self'`** ·
  HSTS · `X-Content-Type-Options: nosniff`។
- **Service Worker បោះបង់សំណើឆ្លង origin** ➜ គ្មានធនធានខាងក្រៅចូល cache។
  ការធ្វើឲ្យសំបកស្រស់ខាងក្រោយមានពេលកំណត់ និងពិដានចំនួនស្របគ្នា ➜ វាមិនអាច
  ស៊ីកូតាការតភ្ជាប់អស់ទេ។

### Firebase Rules

- Root **default-deny**; គ្រប់ node តម្រូវ `auth != null`។
- **Schema validation** — ប្រភេទវាល ជួរតម្លៃ និង `$other: false`។
- **Claim/witness fence** លើការស្តារ និងការលុបទាំងអស់ ➜ replay និងការគិតលុយ
  ស្ទួនកើតមិនបាន។
- Rules **មិន deploy ស្វ័យប្រវត្តិទេ** — ត្រូវ paste ចូល Firebase Console
  រួច Publish ដោយដៃ។

### ព្រំដែនដែលត្រូវដឹង

- **គ្មានតួនាទី** ក្នុង App នេះ — អ្នកប្រើដែលចូលបានមានសិទ្ធិដូចគ្នា។
- ព្រោះគ្មាន backend ដែលទុកចិត្តបាន **អ្នកប្រើអាចសរសេរតួលេខចំណូលដោយផ្ទាល់**
  ហើយ **គ្មានការផ្ទៀងផ្ទាត់ aggregate**។
- **Firebase Config មិនមែនជាសម្ងាត់ទេ** តាមការរចនា — Rules ទើបជាការការពារពិត។
- **តំបន់ម៉ោងរបស់ឧបករណ៍កំណត់ថាចំណូលធ្លាក់ចូលថ្ងៃណា** ➜ ត្រូវបើកមុខងារ
  «កាលបរិច្ឆេទ និងម៉ោងស្វ័យប្រវត្តិ» លើគ្រប់ឧបករណ៍។
- កុំទុក PIN, Config, API secret ឬឯកសារ export លើឧបករណ៍សាធារណៈ។
